================================================================================
  RINGKASAN TEMUAN — PIM (SEMUA FASE)
  Konsolidasi dari docs/TC-PIM.txt
  Project  : qa-portofolio
================================================================================

Dokumen ini adalah ringkasan cepat semua temuan eksplorasi dari seluruh
suite PIM yang sudah diimplementasikan (164 TC total per 2026-11-12, PIM
100% tercakup tanpa gap/finding terbuka: Employee List, Add Employee,
Personal Details + 9 sub-tab termasuk semua 5 sub-section Qualifications
dan Terminate Employment di tab Job, Configuration, Reports, plus 8 TC
security file upload lintas fitur, 2 TC security IDOR/clickjacking, dan
2 TC edge-case refresh/connection-drop). Detail teknis lengkap (locator,
API endpoint, Catatan Eksekusi) tetap ada di dokumen sumber:
docs/TC-PIM.txt.

================================================================================
  FASE 1 — EMPLOYEE LIST, ADD EMPLOYEE, PERSONAL DETAILS (52 TC)
================================================================================

  1. [POLA UI] "Create Login Details" dan radio Gender adalah native input
     yang disembunyikan secara visual di belakang elemen <span>
     custom-styled yang menangkap event klik. Locator role-based
     (getByRole checkbox/radio) tetap BENAR untuk membaca state, tapi
     SALAH untuk melakukan klik — klik harus diarahkan ke <span>
     sibling-nya, bukan ke input aslinya. Klik langsung ke role input
     tidak melempar error, hanya diam-diam tidak mengubah state.

  2. [API] Query param filter Employment Status di Employee List adalah
     `empStatusId`, BUKAN `employmentStatus` seperti dugaan awal dari
     nama field di UI.

  3. [VALIDASI TIDAK KONSISTEN] Employee Id di form Add Employee dibatasi
     10 karakter client-side ("Should not exceed 10 characters"). Employee
     Id di search box Employee List TIDAK dibatasi sama sekali (komponen
     beda, validasi beda) — ID di atas 10 karakter memicu HTTP 422 dari
     server, dan UI diam-diam fallback menampilkan SEMUA record alih-alih
     "No Records Found".

  4. [RACE CONDITION] Form Personal Details terisi secara ASYNC setelah
     URL berubah — membaca value field segera setelah navigasi akan
     mengembalikan string kosong. Solusi: tunggu kondisi yang benar
     secara eksplisit (poll input value), jangan asumsikan urutan event
     selesai begitu URL berubah.

  5. [INFRASTRUKTUR] Server demo publik OrangeHRM sempat terdegradasi
     performanya selama sesi implementasi Fase 1 (ratusan employee dibuat
     berulang kali lewat banyak percobaan run) — bahkan suite Login yang
     sama sekali tidak diubah ikut melambat dan sempat gagal sebagian.
     Pelajaran: selalu bedakan "test gagal karena lingkungan/beban server"
     vs "test gagal karena bug kode/aplikasi" sebelum menyimpulkan apa pun
     dari satu run yang kebetulan berbarengan dengan beban server tinggi —
     verifikasi dengan re-run individual/kecil, jangan langsung percaya
     satu full-run yang gagal.

================================================================================
  FASE 2 — 9 TAB PERSONAL DETAILS LAINNYA (67 TC)
================================================================================

  1. [URL TIDAK KONSISTEN] 2 dari 9 slug URL tab berbeda dari pola yang
     diharapkan:
       - Contact Details  -> "contactDetails" (TANPA prefix "view",
         satu-satunya tab yang begitu; 7 tab lain semua pakai "view...").
       - Report-to        -> "viewReportToDetails" (BUKAN
         "viewReportToList" seperti dugaan awal dari pola nama tab lain).

  2. [KRITIS — DAMPAK LINTAS FASE] Employee Id auto-generate mulai
     BENTROK setelah ratusan employee dibuat sepanjang sesi gabungan
     Fase 1+2. Gejalanya awalnya disangka "server lambat" (timeout
     60-90 detik di waitForResponse POST Add Employee), tapi setelah
     diperiksa screenshot ternyata murni validasi "Employee Id already
     exists" yang memblokir submit di client — request POST-nya memang
     TIDAK PERNAH terkirim, bukan server yang telat merespons. Solusi:
     helper `createTestEmployee()` (src/utils/createTestEmployee.ts) yang
     retry otomatis (clear Employee Id, biarkan client re-generate, maks
     3x) — dipakai di semua TC Fase 2 yang butuh employee baru.

  3. [API] Save di tab Job memicu DUA PUT endpoint sekaligus
     (`job-details` dan `employment-contract`) untuk satu klik Save —
     beda dari Contact Details/Add Employee yang cuma 1 endpoint per Save.

  4. [BUG NYATA DI SITUS ORANGEHRM] Field "Job Specification" di tab Job
     ternyata read-only (menampilkan "Not Defined", bukan field teks).
     Memilih Job Title tertentu memicu GET
     .../job-titles/<id>/specification yang mengembalikan 404 kalau job
     title tsb belum punya dokumen spesifikasi. Console error ini REAL
     (bug aplikasi, bukan noise server), tapi reproduksinya TIDAK 100%
     deterministik: TC-PIM-JOB-01 memilih opsi dropdown ke-2 tanpa nama
     spesifik, jadi hasilnya tergantung Job Title mana yang kebetulan ada
     di posisi itu saat run (diobservasi FAILED di 4 dari 5 run, PASSED
     1x saat 4 Nov 2026 ketika opsi yang kepilih kebetulan sudah punya
     dokumen spesifikasi). Test ini sengaja dibiarkan FAILED (bukan
     `test.fail()`) saat direproduksi, supaya temuannya tercatat otomatis
     di docs/Bug-List.xlsx (lihat README "Auto-close on retest" untuk cara
     Status row-nya menyesuaikan saat test kebetulan passed, tanpa berarti
     bug-nya sudah fix permanen).

  5. [API] PUT contactDetails mengembalikan response body dengan KEY yang
     benar (street1, city, dst) tapi SEMUA VALUE bernilai null — tidak
     meng-echo data yang baru disimpan. Beda dari POST Add Employee
     (Fase 1) yang meng-echo data input apa adanya.

  6. [VALIDASI LONGGAR] Semua field di Contact Details bersifat opsional,
     dan Work Email TIDAK divalidasi format sama sekali — string
     "not-an-email" diterima tanpa error.

  7. [POLA UI BERULANG] Pola hidden-input-di-belakang-<span> yang pertama
     ditemukan di Fase 1 (Create Login Details, Gender) muncul lagi di
     Immigration: radio Document (Passport/Visa) juga native input
     tersembunyi di belakang <span class="oxd-radio-input">.

  8. [VALIDASI CROSS-FIELD] Emergency Contacts punya validasi tidak biasa:
     submit form kosong menghasilkan TEPAT 3 pesan error — 2x "Required"
     (Name, Relationship) + 1 pesan gabungan "At least one phone number
     is required" (validasi OR dari 3 kolom telepon Home/Mobile/Work
     sekaligus, bukan per-kolom).

  9. [STRUKTUR BEDA DARI DUGAAN] Field Name di Report-to BUKAN free text,
     melainkan autocomplete yang me-resolve ke employee sungguhan via
     pencarian async (ada state "Searching...." sebelum hasil muncul).
     Akibatnya TC XSS/SQLi standar tidak relevan di sini — diganti TC
     untuk pencarian nama tidak ditemukan, validasi required, dan
     independensi 2 list (Supervisors vs Subordinates). Submit kosong =
     TEPAT 2 pesan "Required" (Name + Reporting Method).

 10. [SCOPE LEBIH BESAR DARI DUGAAN] Qualifications ternyata punya 5
     sub-section (bukan cuma "Work Experience" + "Education" seperti
     dugaan awal): Work Experience, Education, Skills, Languages,
     License — plus Attachments terpisah (6 tombol "+ Add" total). Fase 2
     hanya mendalami Work Experience secara penuh dan 1 TC representatif
     untuk Education; Skills/Languages/License BELUM dicakup. CATATAN:
     ini TIDAK diselesaikan oleh Fase 3 (lihat bawah) karena Fase 3
     ternyata scope-nya berbeda (Configuration + Reports di PIM, bukan
     sub-section Qualifications ini): masih kandidat perluasan terpisah
     kalau diperlukan.

================================================================================
  FASE 3: PIM CONFIGURATION & REPORTS (29 TC)
================================================================================

  1. [KOREKSI SCOPE] Dugaan awal menempatkan "Configuration" dan "Reports"
     di bawah modul Admin (terpisah dari PIM). Setelah dieksplorasi live,
     ternyata keduanya adalah TAB di dalam PIM sendiri (muncul di top nav
     PIM begitu salah satu tab PIM dibuka, bukan di sidebar Admin). Modul
     Admin punya struktur sendiri yang sama sekali berbeda (User
     Management, Job, Organization, Qualifications, Nationalities,
     Corporate Branding, Configuration dengan 8 sub-item) dan TIDAK
     tersentuh oleh Fase 3 ini: kandidat Fase 4 terpisah kalau
     diperlukan. Pelajaran: dugaan awal yang "masuk akal" tetap harus
     diverifikasi live sebelum dieksekusi, bukan diasumsikan dari nama.

  2. [TEMUAN: UX] Form "Add" di Reports (Report Name + Selection
     Criteria + Display Fields) silently no-op kalau Save diklik tanpa
     menambah satu pun Display Field lewat tombol "+": TIDAK ada request
     POST terkirim DAN TIDAK ada pesan error apa pun yang muncul ke user.
     Form tetap diam di halaman yang sama tanpa penjelasan. Ini kontradiksi
     dengan dugaan awal bahwa cuma Report Name yang wajib diisi.

  3. [POLA UI BARU] Toggle switch di Optional Fields pakai struktur OXD
     yang beda dari checkbox/radio yang sudah ditemukan di fase
     sebelumnya: input native disembunyikan di belakang
     <span class="oxd-switch-input">. Klik ke <span> ini WORK, tapi klik
     ke <div class="oxd-switch-wrapper"> (satu level di atasnya) TIDAK
     mengubah state sama sekali. Klik pertama ke span juga kadang tidak
     teregister kalau dilakukan tepat saat row baru menjadi visible (race
     hydrasi Vue): ditangani dengan retry sampai 3x di page object.

  4. [TEMUAN: SHARED STATE] Toggle Optional Fields (SSN/SIN/Nick Name/dst)
     bersifat SITE-WIDE: mempengaruhi seluruh instance demo publik, bukan
     per-session/per-user. Semua TC di area ini membaca state live sebelum
     toggle dan MENGEMBALIKAN ke state semula di akhir test, supaya tidak
     mengganggu TC lain yang kebetulan berjalan setelahnya atau pengguna
     demo publik lain.

  5. [TEMUAN: KONSISTENSI SERVER] Persistensi toggle Optional Fields
     setelah reload TIDAK KONSISTEN di demo publik ini: PUT
     /api/v2/pim/optional-field selalu sukses (200) dengan urutan kode
     yang identik, tapi efek setelah reload kadang persist kadang tidak,
     diverifikasi berkali-kali secara live dengan kode yang sama persis.
     Kemungkinan eventual-consistency di sisi server demo bersama,
     didokumentasikan via report.finding(), bukan dipaksakan jadi
     report.check() pass/fail tegas.

  6. [VALIDASI TIDAK KONSISTEN ANTAR FITUR SERUPA] 3 fitur CRUD master
     data yang strukturnya identik (Custom Fields, Reporting Methods,
     Termination Reasons) ternyata beda perilaku untuk nama duplikat:
     Custom Fields dan Reporting Methods menolak dengan pesan error
     eksplisit ("Already exists"), sementara Termination Reasons diam-diam
     memblokir submit TANPA pesan error sama sekali: pola yang sama
     dengan temuan Fase 1 soal Employee Id (validasi berbeda untuk
     komponen yang terlihat serupa).

  7. [NOISE INFRASTRUKTUR, BUKAN BUG] Satu kali kegagalan 500 + uncaught
     exception muncul pada TC boundary nama Custom Field 200 karakter,
     TAPI hanya terjadi saat dijalankan paralel bareng TC lain (beban
     server tinggi), tidak pernah reproduce saat dijalankan sendirian
     berkali-kali. Didokumentasikan sebagai kemungkinan race condition di
     sisi server demo bersama, bukan defect validasi panjang nama.

================================================================================
  SECURITY: FILE UPLOAD VALIDATION (CROSS-CUTTING, 8 TC)
================================================================================

  1. [BUG NYATA, TERKONFIRMASI DI 2 TITIK] Upload foto profil (Add
     Employee MAUPUN Personal Details) HANYA memvalidasi ekstensi nama
     file, bukan konten/magic bytes file itu sendiri. File executable
     (.exe) atau Android APK yang di-rename jadi .jpg LOLOS validasi
     tanpa error dan berhasil tersimpan (POST 200), terkonfirmasi di
     kedua titik upload foto. Baseline pembanding membuktikan file .exe
     dengan ekstensi asli memang ditolak, jadi ini murni soal validasi
     yang bisa di-bypass dengan rename sederhana, bukan validasi yang
     tidak ada sama sekali.

  2. [TEMUAN POSITIF] Trik double-extension ("photo.jpg.exe") TIDAK bisa
     bypass, validator cek ekstensi TERAKHIR yang sebenarnya.

  3. [TEMUAN CAMPURAN] Dari 4 titik upload lain yang diuji, bug ini
     meluas ke Personal Details re-upload (sama persis seperti Add
     Employee), TAPI TIDAK meluas ke Attachments Contact Details maupun
     Data Import (keduanya menolak file executable dengan benar). Jadi
     bug ini spesifik ke KEDUA titik upload FOTO PROFIL, bukan ke semua
     fitur upload PIM.

  4. [PELAJARAN DEBUGGING] Beberapa TC sempat terlihat seperti bug
     hang/DoS aplikasi, tapi setelah diisolasi ternyata bug di test kita
     sendiri: `textContent()` tanpa timeout pada locator yang cocok nol
     elemen auto-retry sampai default ~30s. Pelajaran: isolasi dulu
     sebelum menyimpulkan hang = bug aplikasi.

  5. [TEMUAN] <input type="file"> di Personal Details TIDAK melekat ke
     DOM sampai foto (img.employee-image) diklik dulu (count 0 sebelum
     klik, 1 sesudah), ini yang awalnya membuat TC-PIM-PD-13 inconclusive
     sebelum ditemukan pola klik-dulu-nya, dan juga membuat TC-PIM-PD-10
     (reupload foto) lama memakai endpoint yang salah untuk verifikasi
     (PUT .../picture, bukan .../personal-details).

================================================================================
  FASE 4 — SECURITY, EDGE CASE, TERMINATE EMPLOYMENT (5 TC, 2026-11-12)
================================================================================

  1. [BUG SKRIP, POLA BERULANG] Modal "Terminate Employment" di tab Job
     render DI ATAS form Job Details yang masih ada di background --
     background itu punya input "Joined Date" dengan placeholder SAMA
     ("yyyy-dd-mm") plus dropdown/Save button sendiri. Locator tanpa
     scope ke dialog resolve ke 2+ elemen (strict-mode violation).
     Diperbaiki dgn scope semua interaksi modal ke
     `page.getByRole('dialog')`. Root-cause PATTERN-nya identik dgn bug
     skrip Buzz "Edit Post" (2 `<textarea>` di halaman sekaligus) --
     pola umum: modal yang render di atas form background dgn field
     ber-placeholder sama butuh locator yang di-scope ke dialog, jangan
     pernah asumsikan locator global cukup unik.

  2. [TEMUAN APLIKASI] Tombol "Terminate Employment" TIDAK berubah jadi
     "Activate Employment" secara client-side setelah API sukses (200)
     -- butuh reload manual utk melihat state yang benar. Pola SAMA
     dengan temuan Buzz (post baru tidak muncul di feed tanpa reload) --
     app ini secara konsisten tidak melakukan client-side state refresh
     setelah mutasi API sukses.

  3. [TEMUAN MINOR] Section judul di tab Job tertulis "Employee
     Termination / Activiation" -- typo "Activiation" ADA DI APLIKASI
     SENDIRI (dikonfirmasi via screenshot live), bukan kesalahan
     dokumentasi/skrip.

  4. [KONFIRMASI APP-WIDE] Clickjacking header (X-Frame-Options/CSP
     frame-ancestors) hilang di Employee List -- konfirmasi KE-3 dari
     gap yang sama persis juga ditemukan di Login dan Recruitment,
     memperkuat dugaan ini gap konfigurasi level server, bukan kasus
     terisolasi per-modul.

  5. [KONFIRMASI APP-WIDE] Saat koneksi terputus di tengah proses Save
     create-employee, muncul "Uncaught exception: fe" yang identik
     dengan bug yang sama di Admin/Recruitment/Buzz -- dikonfirmasi lbh
     lanjut constructor-nya adalah AxiosError asli (nama ter-minify di
     bundle production), app tetap menampilkan toast error ke user
     (bukan silent failure total), tapi exception tetap bocor ke
     console krn tidak ada `.catch()` lengkap di semua jalur request
     axios. Lihat Bug-List.xlsx BG-201 utk detail lengkap.

================================================================================
  BENANG MERAH ANTAR FASE
================================================================================

  - Pola "jangan asumsikan, verifikasi langsung" terbukti berulang kali
    membongkar kesalahan tebakan: nama slug URL, nama query param API,
    tipe field (dropdown vs text), lokasi klik yang benar untuk
    input tersembunyi, bahkan lokasi menu itu sendiri (Configuration dan
    Reports disangka ada di Admin, ternyata di PIM). Setiap TC yang
    "tampak jelas" dari nama UI-nya tetap diverifikasi live sebelum
    ditulis, dan rencana scope pun tetap diverifikasi ulang kalau ada
    indikasi dugaan awal salah.
  - Infrastruktur demo publik bersama (ratusan employee dan record master
    data dibuat sepanjang sesi Fase 1-3) adalah sumber kegagalan paling
    sering disalahartikan sebagai "server lambat": padahal mayoritas
    kejadian besar ternyata validasi client-side (duplicate ID), bug
    aplikasi nyata (404 Job Specification), atau race condition murni di
    beban paralel (500 di Custom Fields), bukan jaringan/performa server
    semata.
  - Pola hidden-input-di-belakang-elemen-custom (checkbox/radio di Fase 1,
    radio Immigration di Fase 2, switch Optional Fields di Fase 3) terus
    muncul di komponen OXD yang berbeda-beda: library ini konsisten
    menyembunyikan native input di belakang elemen custom-styled untuk
    styling, tapi locator role-based tetap harus diarahkan klik ke elemen
    custom tersebut, bukan ke input aslinya.
  - Validasi tidak konsisten antar fitur yang terlihat serupa adalah pola
    berulang paling sering ditemukan: Employee Id (Fase 1, field beda
    komponen beda validasi), duplicate-name handling (Fase 3, 3 fitur
    CRUD identik struktur tapi beda perilaku). Jangan asumsikan dua
    komponen UI yang terlihat sama akan berperilaku sama.
  - Temuan yang tidak bisa dipastikan "benar/salah" secara tegas
    (format email tidak divalidasi, response tidak echo data, persistensi
    toggle tidak konsisten, dsb) didokumentasikan via `report.finding()`,
    bukan dipaksakan jadi `report.check()` dengan asumsi hasil yang
    "seharusnya".
