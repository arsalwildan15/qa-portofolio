  API ENDPOINT ADD EMPLOYEE (CONFIRMED):
    POST /web/index.php/api/v2/pim/employees
    - Sukses → status 200, body:
        {"data":{"empNumber":N,"lastName":"...","firstName":"...",
                  "middleName":"...","employeeId":"NNNN","terminationId":null},
         "meta":[],"rels":[]}
    - Employee Id duplikat → request TIDAK PERNAH TERKIRIM. Validasi client-
      side memblokir submit dengan pesan "Employee Id already exists" sebelum
      POST dipanggil.
    - Employee Id field: ada BATAS PANJANG 10 KARAKTER client-side — payload
      apa pun di atas 10 karakter (termasuk payload mirip XSS seperti
      "<script>x</script>", 21 char) diblokir oleh validasi panjang dengan
      pesan "Should not exceed 10 characters", BUKAN oleh filter XSS khusus.
      Ini dicatat sebagai temuan di TC-PIM-ADD-20, bukan bukti proteksi XSS
      yang sesungguhnya — payload XSS yang MUAT di bawah 10 karakter belum
      tentu tertangkap.
    - Whitespace-only First/Last Name → di-trim client-side jadi kosong,
      memicu validasi "Required" sama seperti pola di Login (TC-LOGIN-15/16).

  API ENDPOINT EMPLOYEE LIST (CONFIRMED):
    GET /web/index.php/api/v2/pim/employees?limit=50&offset=0&model=detailed
        &includeEmployees=onlyCurrent&sortField=employee.firstName&sortOrder=ASC
    - Filter Employment Status → query param sebenarnya adalah `empStatusId`,
      BUKAN `employmentStatus` (ditemukan salah asumsi awal, dikoreksi di
      TC-PIM-LIST-03 — pelajaran yang sama seperti kasus username
      case-insensitive di Login: verifikasi langsung, jangan asumsi nama
      param dari UI label).
    - Search Employee Id TIDAK PUNYA batas panjang client-side (beda dari
      Employee Id di form Add Employee yang dibatasi 10 karakter) — ID
      pencarian >10 karakter mengembalikan HTTP 422 dari server, dan UI
      diam-diam fallback menampilkan SEMUA record alih-alih "No Records
      Found". TC-PIM-LIST-09 disesuaikan memakai ID valid (bukan >10 char)
      dan mendokumentasikan perilaku 422-silent-fallback sebagai temuan
      terpisah.

  LOCATORS & PERILAKU KONFIRMASI (EmployeeListPage.ts):
    4 dropdown filter (Employment Status, Include, Job Title, Sub Unit) di-
    scope lewat teks label persis (.oxd-input-group berisi label exact),
    BUKAN index posisi .nth() — percobaan awal pakai index terbukti tidak
    reliable karena urutan DOM tidak selalu sama dengan urutan visual di
    semua kondisi layar/loading.
    Modal konfirmasi delete: tombol "Yes, Delete" / "No, Cancel" (dikonfirmasi
    teks persis, beda dari asumsi awal "Yes"/"No" polos).
    [TEMUAN BELUM TUNTAS] Header kolom sort (mis. "Id") punya trailing space
    di accessible name, dan filter hasText:'Id' ikut mencocokkan substring di
    dalam "Middle" (dari "First (& Middle) Name"). exact:true maupun
    getByText(exact) tetap gagal isolasi satu elemen. TC-PIM-LIST-07
    sementara didokumentasikan sebagai finding (elemen trigger sort belum
    teridentifikasi pasti), bukan hard-fail — butuh investigasi manual
    DevTools lebih lanjut di sesi terpisah.

  LOCATORS & PERILAKU KONFIRMASI (PersonalDetailsPage.ts):
    Form Personal Details TERISI ASYNC setelah navigasi — URL berubah ke
    /viewPersonalDetails/empNumber/N LEBIH DULU, baru kemudian field terisi
    dari GET .../personal-details yang menyusul. Membaca value field segera
    setelah waitForURL() mengembalikan string kosong. WAJIB pakai
    waitUntilLoaded() (poll inputValue() first name sampai tidak kosong,
    timeout 15s) sebelum membaca/assert field apa pun di halaman ini.
    Gender radio (Male/Female): SAMA PERSIS seperti "Create Login Details" —
    input dengan role="radio" tersembunyi visual di belakang
    <span class="oxd-radio-input"> yang menangkap klik. check()/click() pada
    role="radio" langsung timeout atau tidak mengubah state Vue walau dengan
    {force:true}. WAJIB klik sibling <span>-nya (lihat
    clickMaleRadio()/clickFemaleRadio()).
    Filter hasText:'Male' pada .oxd-radio-wrapper JUGA mencocokkan radio
    Female (satu wrapper group berisi kedua label) — strict-mode violation
    kalau dipakai sembarangan; locator produksi pakai role=radio dengan nama
    exact untuk baca checked state.

================================================================================
  TEMUAN SELAMA EKSPLORASI (bukan bug di test kita, tapi worth dicatat)
================================================================================

  1. "Create Login Details" dan Gender radio adalah native input YANG
     DISEMBUNYIKAN SECARA VISUAL di belakang <span> custom-styled yang
     menangkap event klik — pola OXD component yang BERBEDA dari pola input
     biasa. Playwright role-based locator (getByRole checkbox/radio) tetap
     BENAR untuk membaca state, tapi SALAH untuk klik — harus klik
     elemen <span> sibling-nya.

  2. Query param filter Employment Status sebenarnya `empStatusId`, bukan
     `employmentStatus` seperti dugaan awal dari nama field di UI.

  3. Employee Id di form Add Employee dibatasi 10 karakter client-side;
     Employee Id di search box Employee List TIDAK dibatasi sama sekali
     (beda komponen, beda validasi) dan ID >10 char memicu HTTP 422 yang
     di-silent-fallback oleh UI jadi menampilkan semua record.

  4. Personal Details form mengalami race condition yang mirip (tapi
     kebalikan arah) dengan lesson #6 di TC-Login.txt: di sana masalahnya
     "action sebelum goto() selesai", di sini masalahnya "baca value
     sebelum fetch async selesai" — keduanya solusinya sama: tunggu
     kondisi yang benar secara eksplisit, jangan asumsikan urutan event.

  5. Server demo publik OrangeHRM sempat terdegradasi performanya saat sesi
     implementasi ini berjalan (ratusan employee dibuat berulang kali lewat
     banyak percobaan run) — bahkan suite Login yang sama sekali tidak
     diubah ikut melambat dan sempat gagal sebagian saat demo lambat. Ini
     bukti pentingnya membedakan "test gagal karena lingkungan" vs "test
     gagal karena bug kode/aplikasi" sebelum menyimpulkan apa pun dari satu
     run yang kebetulan berbarengan dengan beban server tinggi.
